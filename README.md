# Structure of project

## Concept

The game will be released on http://itch.io/.

The idea of Dixvoice is a clever twist on the famous Dixit game, where players use and generate audio clips instead
of cards.

Each audio clip will be no more than 2 seconds long.

As with Dixit where players have 6 cards, players have 6 sound clips of up to 2 seconds: 5 dealt from an already
generated list, and 1 they can generate themselves. Other players cannot tell whether a clip was generated by its
owner or dealt from the list.

## Game rules

The game follows Dixit, with sound clips instead of cards.

Terms, from largest to smallest:

- **Session**: the lifetime of a room, from its creation to its deletion. A session contains one or more games. Sound
  ids already used in the session are tracked by the backend (see Back-End).
- **Game**: from pressing Start until a player reaches the target score (or the game is stopped). A game contains one
  or more rounds. Scores reset at the start of each game.
- **Round**: one set of hands dealt to the players, played through by one storyteller in the 4 phases below. Rounds are
  numbered from 1 within each game.

- **Players**: 4 minimum, 8 maximum per room.
- **Hand**: 6 slots per player.
  - 5 **dealt** slots, filled from the room's pool (the audio service's list of existing sounds, shuffled). A clip is
    never dealt twice in a session, so it is never in two hands at once.
  - 1 **custom** slot, filled by the player by generating their own sound (text + tonality). It is optional: it stays
    empty until the player generates a sound, which they can do at any time during the round while it is empty (until
    they have submitted their clip). Generation runs in the background and never blocks the round.
- **Round**, the same phases as Dixit:
  1. **Storyteller**: the storyteller picks one clip from their hand and writes a text clue. Only the clue is shown to
     the others; the chosen clip stays hidden (face down).
  2. **Submit**: every other player picks the clip from their hand that best matches the clue, also face down.
  3. **Vote**: all submitted clips are shuffled and shown anonymously. Every player except the storyteller votes for the
     clip they think is the storyteller's. A player cannot vote for their own clip.
  4. **Reveal**: everyone sees who submitted which clip and who voted for what, and scores are updated.
- **Scoring** (Dixit rules):
  - if every player or no player finds the storyteller's clip, the storyteller scores 0 and everyone else scores 2;
  - otherwise the storyteller and each player who found the clip score 3;
  - every player other than the storyteller also scores 1 point per vote their own clip received.
- **Fresh hands every round**: each round starts with a completely new hand. At the end of the round, every clip that
  was in a hand (played or not) is discarded for the rest of the session and never comes back. Each player is dealt 5
  clips nobody has seen yet, and the custom slot is emptied (the player can generate a new sound for the new round).
- **Next round**: the storyteller role passes to the next player in join order (the first storyteller is picked at
  random). Any player can press "Next round" once the reveal is shown. There are no timers.
- **End of game**: the game ends after the reveal in which one or more players reach **10 points**; the highest score
  wins (ties share the win). It also ends early if the pool does not have enough unseen clips to deal the next round (5 per player).

## Rooms

- Any player can **create a room**. The backend returns a short room code (e.g. 4 letters) to share with the others.
  Several rooms can exist at the same time.
- Players **join with the code** and a nickname. Joining fails if the code does not exist, if the room already has 8
  players ("no more room"), or if the game has started.
- **Any player can press Start** once at least 4 players are in the room. Starting the game **locks the room**: nobody
  new can join.
- **Any player can press Stop**. Stopping ejects everybody and **deletes the room**.
- A room is also deleted when its last player leaves.
- After the end of a game, players stay in the room and see the final scores. Any player can start a new game with the
  same players (scores reset, discarded clips stay discarded) or stop to delete the room.
- If a player's connection drops, they keep their seat and can reconnect with their session token, even while the room
  is locked.

## Web App

We are going to be build a web app, with golang backend and vite.js react frontend.

### Front-End

Root dir: ./webapp/frontend

A player can start a game.

The frontend is a Vite + React single-page app, built as a static bundle so it can be uploaded to itch.io as an HTML5
game. It holds no game logic: it renders the state sent by the backend and sends player actions back.

Layout and styling:

- **Mobile first**: the game must be fully playable on a phone in portrait orientation (from 360px wide), both in a
  mobile browser and in the itch.io embed, and scale up to tablet and desktop.
- Touch-friendly: tap targets of at least 44px, no hover-only interactions, no horizontal scrolling. The hand of 6
  clips stacks or wraps on narrow screens.
- **Basic styling only** for this first version: plain CSS, a neutral palette and system fonts, no UI framework or
  custom assets. Keep colors and spacing in CSS variables so the game identity can be applied later without
  restructuring the components.

Screens and features:

- **Home**: enter a nickname, then either create a room or join one with a code. Show the join errors clearly (unknown
  code, room full: "no more room", game already started).
- **Lobby**: show the room code (easy to read aloud and copy), the connected players, a Start button (enabled with 4+
  players), a Stop button and a Leave button.
- **Hand**: the player's 6 slots as cards; tapping a card plays its sound. The custom slot shows its state: empty (with
  a "Create a sound" action), generating, ready, or failed (with a retry). Only the owner sees which clip is custom.
- **Create a sound**: a form with a text field and a tonality field, sent to the backend.
- **Round screens**, one per phase (see Game rules): the storyteller picks a clip and writes a clue; the others pick a
  clip; everyone votes on the shuffled clips; the reveal shows owners, votes and points won. Show who has already
  submitted or voted so players know who they are waiting for.
- **Scoreboard** always reachable during the game, and an end-of-game screen with the final scores, "New game" and
  "Stop".
- A **Stop** button is available during the game too; it asks for confirmation in the page (no browser dialog).

Audio playback:

- Clips are fetched directly from the audio service with `GET {AUDIO_SERVICE_URL}/audio/{id}` and played with an HTML
  `<audio>` element. The frontend never calls `POST /audio` (the backend does).
- Browsers block audio until the user interacts with the page, so playback always starts from a tap.

Configuration (build-time env vars):

- `VITE_BACKEND_URL`: base URL of the backend (HTTP and WebSocket).
- `VITE_AUDIO_SERVICE_URL`: base URL of the audio service.
- Vite `base: './'` so the built bundle works from the itch.io zip upload.

On itch.io, the upload must have "Mobile friendly" checked and a fullscreen button enabled.

### Back-End

Root dir: ./webapp/backend

Manages basic multiplayer through rooms (see Rooms).

The backend is a Go server and is the single source of truth for every room and game. All state lives in the
backend's memory for now; a database comes later.

Responsibilities:

- **Rooms and players**: create rooms and codes, handle joins (enforcing the 8-player limit and the lock), leaves,
  reconnects, start and stop, and delete rooms that are stopped or empty.
- **Real-time sync**: one WebSocket connection per player. After every change, the server sends each player of the
  room a fresh state snapshot built for that player (see Protocol). Each player only receives what they are allowed
  to see: their own hand, who owns which submitted clip only at the reveal, and never whether another player's clip
  is custom.
- **Used sounds**: each room keeps the set of every sound id already used in it: every clip dealt into a hand and every
  custom sound generated by its players. The set lives as long as the room: it carries over from one game to the next in
  the same room, and is deleted with the room. Rooms never share it, so the same sound can appear in two different
  rooms.
- **Game rules**: deal a fresh hand every round from `GET /audio/list` minus the room's used sounds (shuffled), add
  the dealt clips to the used sounds, rotate the storyteller, enforce phase order, validate every action (right phase, right player, clip in hand, no
  self-vote), score each round and detect the end of game.
- **Sound generation**: on a player's request, call `POST /audio` on the audio service, then put the returned clip in
  the player's custom slot. Only the backend calls the POST endpoint.

#### Protocol

All JSON. Errors from HTTP endpoints use the same error codes as the WebSocket `error` message.

HTTP:

| Method and path | Body | Response |
| --- | --- | --- |
| `POST /rooms` | `{"nickname": "Ana"}` | `201 {"roomCode": "KXQP", "playerId": "p1", "token": "..."}` |
| `POST /rooms/{code}/join` | `{"nickname": "Ben"}` | `200 {"roomCode": "KXQP", "playerId": "p2", "token": "..."}` |
| `GET /healthz` | | `200` |

Join errors: `404 room_not_found`, `409 room_full`, `409 game_started`, `400 invalid_nickname`.

WebSocket: `GET /ws?token=...`. The token identifies both the player and the room. Reconnecting with the same token
gives the player their seat back. On connection, the server immediately sends a `state` message.

Client to server (`{"type": ..., ...}`):

| Type | Fields | Allowed |
| --- | --- | --- |
| `start_game` | | lobby or finished, 4+ players |
| `stop_game` | | any time |
| `leave_room` | | lobby or finished |
| `generate_sound` | `text`, `tonality` | custom slot empty |
| `submit_clue` | `clipId`, `clue` | storyteller, phase `storyteller` |
| `submit_clip` | `clipId` | non-storyteller, phase `submit`, once |
| `vote` | `clipId` | non-storyteller, phase `vote`, once, not own clip |
| `next_round` | | phase `reveal` |

Server to client:

- `state`: the full snapshot for this player (below), sent after every change.
- `error`: `{"type": "error", "code": "not_your_turn", "message": "..."}`, sent only to the player whose action was
  rejected. Codes include `invalid_phase`, `not_your_turn`, `clip_not_in_hand`, `already_submitted`, `cannot_vote_own`,
  `not_enough_players`, `custom_slot_busy`, `generation_failed`.
- `room_closed`: `{"type": "room_closed", "reason": "stopped"}`, then the server closes the socket. The frontend
  returns to the Home screen.

State snapshot:

```json
{
  "type": "state",
  "room": { "code": "KXQP", "status": "lobby | playing | finished", "targetScore": 10 },
  "you": {
    "playerId": "p1",
    "hand": [ { "clipId": "a12", "custom": false } ],
    "customSlot": "empty | generating | ready | failed"
  },
  "players": [
    { "playerId": "p1", "nickname": "Ana", "connected": true, "score": 12,
      "isStoryteller": true, "hasSubmitted": true, "hasVoted": false }
  ],
  "round": {
    "number": 3,
    "phase": "storyteller | submit | vote | reveal",
    "storytellerId": "p1",
    "clue": "a door in the rain",
    "yourSubmission": "a12",
    "yourVote": null,
    "table": [ { "clipId": "a12" }, { "clipId": "b07" } ],
    "reveal": {
      "results": [ { "clipId": "a12", "ownerId": "p1", "isStoryteller": true, "voterIds": ["p2"] } ],
      "points": { "p1": 3, "p2": 3 }
    }
  },
  "winnerIds": []
}
```

- `round` is `null` in the lobby. `clue` is `null` until the storyteller submits it. `table` is empty until the vote
  phase. `reveal` is `null` until the reveal phase.
- `hand` has up to 6 entries; `custom: true` marks the custom slot and is only ever sent to its owner.
- `winnerIds` is filled when `room.status` is `finished`.

#### Deployment

The backend ships as a container image (multi-stage `Dockerfile` in `./webapp/backend`: build the Go binary, then copy
it into a minimal runtime image) and runs on the existing gcast Kubernetes cluster:

- **Deployment** with exactly **1 replica**: all rooms live in memory, so a second replica would not see the rooms of
  the first.
- **Service** exposing the HTTP and WebSocket endpoints inside the cluster. Public exposure (Ingress, HTTPS) comes at a
  later stage; it will need to allow WebSocket upgrades and long-lived connections. Until then, test with
  `kubectl port-forward`.
- **Configuration** through environment variables: `PORT`, `AUDIO_SERVICE_URL`, and `ALLOWED_ORIGINS` (CORS and
  WebSocket origin check; the itch.io domains the frontend is served from, plus `http://localhost:5173` for dev).
- **Health check**: `GET /healthz` for liveness and readiness probes.
- Kubernetes manifests in `./webapp/backend/k8s`.

A restart of the pod deletes every room and game in progress, which is acceptable for the hackathon.

## Audio Generator Microservice

The audio generator microservice has 3 endpoints:

- GET: /audio/list: list all possible sound objects in JSON
- GET: /audio/{id}: returns the mp3 file for a given audio sound
- POST: /audio: create a new sound from text and tonality

The frontend uses the GET endpoints; only the backend calls the POST endpoint. The service must therefore allow CORS
from the frontend's origins for the GET endpoints.

### Placeholder schemas

Until the audio service defines its own, the web app assumes:

- `GET /audio/list` → `200 [ { "id": "a12" } ]` (other fields are ignored by the web app).
- `GET /audio/{id}` → `200` with `Content-Type: audio/mpeg`, a clip of at most 2 seconds.
- `POST /audio` with `{ "text": "a door creaking in the rain", "tonality": "eerie" }` → `201 { "id": "c31" }`.
  Generation may take several seconds. `tonality` is free text for now.
- Generated sounds must be indistinguishable from listed ones through the ids and the GET endpoints, so other players
  cannot tell a custom clip apart.

For local development and tests, the backend includes a mock audio service (a fixture list and a few sample mp3 files)
selected by setting `AUDIO_SERVICE_URL` to it.
